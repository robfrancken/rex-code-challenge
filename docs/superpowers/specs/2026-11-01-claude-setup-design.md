# Claude Code setup — design

- **Date:** 2026-11-01
- **Status:** draft, awaiting approval
- **Scope:** the commits that follow `Initial Laravel scaffold` and come before any product code

## Intent

The Rex technical exercise asks for a Laravel contacts module (API + CLI) and a React SPA, submitted as one PR, plus a README explaining how AI was used "without compromising on the outcome".

Before any product code is written, Rob wants a committed Claude Code setup that:

- keeps Claude away from destructive commands,
- encodes the architecture (DDD modules, colocated tests) so Claude builds the way Rob would,
- gives one entry point, `/feature`, that scales its process to the size of the task,
- reviews its own work for DRY, SOLID and OWASP problems,
- enforces commit format and linting mechanically rather than by request,
- hardens the JavaScript supply chain through pnpm.

The setup is itself part of the submission: it showcases Claude Code knowledge (permissions, hooks, rules, skills) to reviewers. The brief describes teams of 4–5 engineers per repo, so it should read as something a team could adopt.

## Goals

1. Claude cannot run `rm -rf` (in any spelling) or other work-destroying commands.
2. Architecture and testing conventions live in `.claude/rules/` and load automatically.
3. `/feature <task>` sizes the task, then runs the right amount of process; large tasks get a dependency tree showing what can run in parallel.
4. DRY, SOLID, OWASP-backend and OWASP-frontend review skills exist and `/feature` uses them.
5. pnpm replaces npm, with supply-chain protections switched on, and every dependency change asks Rob first.
6. Lint runs on every file Claude edits; commit messages are checked before the commit happens.
7. Tests live next to the code they test, and the test runner finds them there.

## Non-goals

- The contacts module itself. It is built afterwards, with `/feature`.
- Frontend setup (React, TypeScript, TanStack Query, Axios, shadcn/ui). It is a separate, later commit.
- Enforcing anything on human commits. Git hooks and CI are out of scope; the hooks target Claude only.
- Changing `CLAUDE.md` or `AGENTS.md`. Both are generated by Laravel Boost and get regenerated.

## Anti-goals

- Ceremony on trivial tasks. A one-line fix must not trigger a spec and plan.
- Naming Paradev, Superset or any other parallel-run tool anywhere in the setup. Each developer has their own workflow. Superpowers skills may be named.
- Duplicating guidance that the installed Boost skills already give (for example `laravel-best-practices/rules/security.md`). Reference it instead.
- Hooks that noticeably slow every edit.
- Hooks that block legitimate work so often they get disabled.

## Rob's decisions

1. **Commit format:** `<branch>: <description>`, for example `REX-0001: initial claude setup`.
2. **Hooks:** lint and commit checks are Claude Code hooks in `.claude/hooks/`, to showcase Claude Code.
3. **Module layout:**

   ```
   app/Modules/<Module>/
   ├── Application/
   │   ├── Actions/        UpsertContact.php
   │   ├── Assemblers/     ContactDataFromRequest.php, ContactDataFromCli.php
   │   ├── DTOs/           UpsertContactData.php
   │   └── Validation/     ContactValidator.php
   ├── Domain/
   │   └── Models/         Contact.php, ContactEmail.php, ContactPhone.php
   └── Presentation/
       ├── Http/Controllers/   ContactController.php
       └── Console/Commands/   UpsertContactCommand.php
   ```

4. **Validation:** one validator per use case, shared by HTTP and CLI, so both entry points enforce identical rules.
5. **Assemblers:** they build a DTO from one input source and are named for it: `ContactDataFromRequest`, `ContactDataFromCli`.
6. **Colocated tests:** `UpsertContactTest.php` sits next to `UpsertContact.php`, not under `tests/`. The same applies on the frontend.
7. **`/feature`:** sizes the task. Trivial tasks are just done. Larger tasks go through brainstorming, spec and plan. Large tasks also get a dependency tree for parallel work. The skill may name superpowers skills.
8. **Review skills:** DRY, SOLID, OWASP for the backend, OWASP for the frontend.
9. **Package manager:** pnpm, for its supply-chain protections.
10. **Work order:** Claude setup → backend/CLI contacts module → frontend setup commit → frontend features.
11. **Test database isolation:** the base `TestCase` uses `RefreshDatabase`, which migrates once and then gives each test its own transaction. Individual tests never import a database trait. This is a rule.
12. **Branch:** keep `REX-0001`.
13. **Frontend stack (for the later commit):** React, TypeScript, Vite, TanStack Query, Axios, shadcn/ui. No Laravel starter kit, no Inertia, no Redux or Zustand. React Router not initially.

## Design

### Branch and commits

Work continues on Rob's existing branch, `REX-0001`, after `REX-0001: sensible claude permissions`. Rob chose to keep this name. Suggested commits:

1. `REX-0001: claude setup design spec`: this document, in its own commit.
2. `REX-0001: initial claude setup`: settings, hooks, rules, skills.
3. `REX-0001: switch to pnpm with supply-chain hardening`
4. `REX-0001: colocate tests with source`

### 1. Settings (`.claude/settings.json`)

- Keep Rob's existing allow and deny entries.
- **Deny list (first layer).** Add entries that block recursive `rm` regardless of path (`rm -rf`, `rm -fr`, `rm -r`, `rm -R` prefixes) and `npm`, `npx` and `yarn`. Deny entries only match the start of a command, so the hooks below are the real guard.
- **Allow list.** Add the read-only and quality commands Claude runs constantly: Pest and `php artisan test`, Pint, `php artisan route:list` / `config:show` / `about`, `composer show`, and `composer dump-autoload`.
- **Ask list.** `ask` rules take precedence over allow rules. They make edits to the files that hold the guards always prompt: `pnpm-workspace.yaml`, `.npmrc`, `.claude/settings.json` and `.claude/hooks/**`. This protection is a permission rule rather than a hook on purpose: if the hooks guarded their own files, Claude could disable a hook and then edit freely. Add these rules as the last step of the setup work, so building the hooks doesn't prompt on every change.
- **Dependency changes** are gated by the `ask-dependency-change.sh` hook (below), not by `ask` rules.
- **Hooks.** Register the hooks below with `$CLAUDE_PROJECT_DIR`-based paths.
- **Plugins.** Declare superpowers (`superpowers@claude-plugins-official`) under `enabledPlugins`, so anyone who opens the repo in Claude Code is prompted to install it, and `/feature` works for a reviewer or teammate who clones it. Check against the Claude Code docs whether the official marketplace also needs an `extraKnownMarketplaces` entry.

### 2. Hooks (`.claude/hooks/`)

Each hook is a small single-purpose bash script. It reads the hook's JSON input on stdin with `jq`, and when it blocks, it gives a reason Claude can act on (exit code 2 with a message, or the JSON deny decision).

| Script | Event / matcher | Behaviour |
|---|---|---|
| `guard-destructive.sh` | PreToolUse, `Bash` | Checks every part of a compound command (`&&`, `;`, `\|`, subshells, `bash -c`) and blocks anything that destroys work. **Files:** any recursive `rm`, with or without force, in every spelling (`-r`, `-R`, `-rf`, `-fr`, `-Rf`, `-r -f`, `--recursive`), plus `find … -delete` and `find … -exec rm`. **Git:** `git clean -f…`, `git reset --hard`, force-pushes (`--force`, `-f`, `+refspec`), `git stash drop` and `git stash clear`, `git branch -D`, and discarding uncommitted changes with `git checkout -- <path>` or `git restore <path>` (any path; `git restore --staged` is allowed). **Database:** `php artisan db:wipe`, `migrate:fresh` and `migrate:reset`. The message suggests a safe alternative: `git rm`, deleting a single named file, or asking the user. |
| `ask-dependency-change.sh` | PreToolUse, `Bash` and `Edit\|Write\|MultiEdit` | Returns an **ask** decision (not a block), with a reason that names what is changing, so Rob approves every dependency change. **Commands**, anywhere in a compound command: `pnpm add`, `pnpm install <pkg>` / `pnpm i <pkg>`, `pnpm update` / `up`, `pnpm remove` / `rm`, `pnpm dlx`, `pnpm approve-builds`, `composer require`, `composer remove`, `composer update`. Plain `pnpm install` and `composer install` from the lockfile pass through. **Files:** any edit to `package.json` or `composer.json`, since a hand-edited dependency followed by a plain install would otherwise slip through. This overrides Rob's `Bash(pnpm *)` and user-level `Bash(composer *)` allows for these cases. |
| `enforce-pnpm.sh` | PreToolUse, `Bash` | Blocks `npm`, `npx` and `yarn` used as a command anywhere in a compound command. The message points to `pnpm`, `pnpm exec` and `pnpm dlx`. |
| `commit-format.sh` | PreToolUse, `Bash` (only acts on `git commit`) | Blocks commits on `main`/`master`. Requires the subject line to be `<current-branch>: <non-empty description>`. Must read messages given as `-m '…'`, `-m "…"`, and the heredoc form `-m "$(cat <<'EOF' … EOF)"`. If the message source can't be determined (editor commit, `-F`), it blocks and asks Claude to use `-m`. `--amend --no-edit` is allowed. |
| `lint-php.sh` | PostToolUse, `Edit\|Write\|MultiEdit` on `*.php` | Runs `vendor/bin/pint` on the edited file. If Pint can't fix it (for example a parse error), it reports back so Claude fixes it immediately. |
| `lint-frontend.sh` | PostToolUse, `Edit\|Write\|MultiEdit` on `*.ts`, `*.tsx`, `*.js`, `*.jsx` | If the frontend linter and formatter aren't installed yet, it exits quietly. Once the frontend commit installs them, it formats the file and auto-fixes lint, and reports anything that can't be auto-fixed. |

**Testing the hooks.** Each script has a colocated test (`guard-destructive.test.sh` next to `guard-destructive.sh`) in plain bash. A test pipes fixture JSON into the hook and asserts the exit code. Tests cover blocked cases and must-allow cases (`git rm file`, `rm single-file.txt`, `pnpm install`, `git push`, a correctly formatted commit). A single runner script runs them all.

**Known trade-off.** The destructive-command guard is conservative: text inside quotes is still checked, so a command that only *mentions* `rm -rf` in a string (an `echo`, a commit message) is blocked. That is accepted, because stripping quotes would let `bash -c "rm -rf …"` through. The tests document it.

### 3. Rules (`.claude/rules/`)

These are Claude Code's native project rules, loaded automatically. Where a rule only concerns some files, it uses `paths:` frontmatter so it loads only when those files are in play.

- **`architecture.md`** (`app/**`):
  - Module layout as above. Dependencies point inward: Presentation → Application → Domain. Domain never uses Application or Presentation.
  - Entry points (controllers, commands, jobs) stay thin: validator → assembler → DTO → Action → format output. No business logic in Presentation.
  - Actions do one thing, take typed DTOs and return typed results. An Action that writes to more than one table wraps the work in one `DB::transaction`.
  - DTOs are `final readonly` classes with typed properties. No raw arrays cross into Actions.
  - Eloquent models live in `Domain/Models`, as a pragmatic concession rather than strict DDD.
  - Each module has its own service provider that registers its routes and commands. The provider is listed in `bootstrap/providers.php`, which is Laravel's convention. That one line is the only central file a new module touches. No custom module loader.
  - Modules talk to each other only through the other module's Application layer.
- **`testing.md`** (`app/**`, `resources/js/**`, `tests/**`):
  - Tests are colocated: `XTest.php` next to `X.php`, and `X.test.tsx` next to `X.tsx`.
  - `tests/` holds only `TestCase.php`, `Pest.php` and the architecture tests.
  - Database isolation belongs to the base `TestCase`, which uses `RefreshDatabase`. Individual tests never import or `uses()` a database trait.
  - Points to the `testing-best-practices` skill for how to write tests.
- **`commits.md`** (always loaded): the `<branch>: <description>` format, never committing on `main`, and one commit per completed task. The hook enforces this; the rule explains it so Claude gets it right first time.
- **`package-management.md`** (`package.json`, `pnpm-*`, `resources/js/**`): pnpm only (`pnpm dlx`, not `npx`). Never weaken or bypass the release-age or build-script settings. New dependencies need approval.

### 4. Skills (`.claude/skills/`)

**`feature`**: invoked as `/feature <task description or ticket>`.

1. **Branch.** If on `main`, create a branch named after the ticket key. If there's no key, ask for one.
2. **Size.** Classify the task, say which size it picked and why, and let Rob override:

   | Size | Signals | Process |
   |---|---|---|
   | Trivial | one obvious change, no design decision | `superpowers:test-driven-development` → review → commit |
   | Medium | a few files, one or two decisions | `superpowers:brainstorming`, with the design agreed in chat and no spec document → TDD → review → commit |
   | Large | several components, layers or entry points | `superpowers:brainstorming` with a written spec → `superpowers:writing-plans`, with a dependency tree (below) → execute with `superpowers:subagent-driven-development` or `superpowers:executing-plans`, as the developer prefers → review → commit per task |

3. **Dependency tree** (large tasks only). The plan gets a section listing each task with:
   - **ID**
   - **Depends on**
   - **Touches:** the files or module areas it changes
   - **Wave:** wave 1 has no dependencies, and wave *n* depends only on earlier waves

   Tasks in the same wave must not touch overlapping files. Present it as a table plus a Mermaid graph, which renders in the PR. Describe it neutrally ("these can run in parallel") and never name a tool for running them.
4. **Review.** Before each commit, run the review skills that match the changed files:
   - backend: DRY, SOLID, OWASP-backend
   - frontend: DRY, SOLID, OWASP-frontend

   Fix the findings, then run `superpowers:verification-before-completion`.

**Review skills:** `review-dry`, `review-solid`, `review-owasp-backend`, `review-owasp-frontend`. Each one:

- says when to use it, so Claude can also reach for it unprompted, and can be run on its own;
- gives a checklist tailored to this stack (Laravel 13 / PHP 8.5, or React + TypeScript);
- returns findings as file:line, severity and suggested fix;
- says what *not* to flag. For example, DRY doesn't merge coincidental duplication (rule of three), and SOLID doesn't demand interfaces with one implementation.

DRY and SOLID cover both stacks, with a backend section and a frontend section each:

- **`review-dry`:**
  - backend: validation rules, query logic, and mapping between DTOs and models;
  - frontend: API calls belong in one client or query-hook layer, types are shared rather than redeclared, and repeated JSX patterns become components.
- **`review-solid`:**
  - backend: Actions, DTOs, providers and interfaces;
  - frontend:
    - single responsibility for components and hooks;
    - extending through composition rather than flags or conditionals;
    - narrow prop types (interface segregation);
    - components depend on query hooks, not directly on Axios (dependency inversion).

Only OWASP is split by stack, because the threats differ on each side. What each OWASP skill covers:

- **`review-owasp-backend`:** the OWASP API Security Top 10 applied to Laravel: object-level authorisation, mass assignment, injection, rate limiting, error responses that leak internals, and validation of third-party input. It references `laravel-best-practices/rules/security.md` rather than repeating it.
- **`review-owasp-frontend`:** XSS (including `dangerouslySetInnerHTML`), token storage, CSRF with Laravel's session cookies, open redirects, secrets in the bundle, and dependency risk.

### 5. pnpm switch and supply-chain hardening

- Convert the lockfile with `pnpm import`, then `git rm package-lock.json`.
- Reinstall `node_modules` with pnpm without using `rm -rf`. pnpm can purge the npm layout itself; use its non-interactive option.
- Set `packageManager` to `pnpm@11.1.2` in `package.json`.
- Put the settings in `pnpm-workspace.yaml`. Check the exact names against the pnpm 11 docs, since pnpm 11 moved settings out of `.npmrc`. The intent:
  - packages must be at least **7 days** old before they can be installed (`minimumReleaseAge`);
  - dependency build scripts are off, except an explicit allowlist (currently expected to be empty);
  - installs fail on an unapproved build script rather than silently skipping it;
  - trust policy: no installing a version with weaker provenance than earlier versions;
  - block exotic transitive sources (git URLs, tarballs).

  Keep `.npmrc` only for anything pnpm 11 still reads from it.
- Switch the `composer.json` `setup` script from `npm` to `pnpm`.
- **Verify:** `pnpm install --frozen-lockfile` and `pnpm build` succeed.

### 6. Colocated test configuration

- **`phpunit.xml`.** Replace the `Unit` and `Feature` suites with:
  - one suite that discovers `*Test.php` under `app/`;
  - one `Arch` suite for `tests/Arch`.

  Exclude `*Test.php` from `<source>`, so tests don't count toward coverage.
- **`tests/Pest.php`.** Bind `TestCase` to the `app/` tree (`->in('../app')`) and to `tests/Arch`, and drop the boilerplate (`toBeOne`, `something()`).
- **`tests/TestCase.php`.** Uses `RefreshDatabase` (Rob's decision). In Laravel 13 it migrates once per test run, including for in-memory SQLite, and then wraps each test in a transaction that is rolled back. It works the same however the tests are started (`composer test`, `php artisan test --filter`, `vendor/bin/pest`, the IDE). `phpunit.xml` keeps `DB_DATABASE=:memory:`.
- **Example tests.** Delete `tests/Feature/ExampleTest.php` and `tests/Unit/ExampleTest.php`.
- **`tests/Arch/ArchitectureTest.php`.** Turns the layer rules into failing tests: Domain doesn't use Application or Presentation, and Application doesn't use Presentation. It must pass while `app/Modules` is still empty. Add Pest's `php` and `security` presets if they pass on the skeleton.
- **Verify:**
  - `composer dump-autoload -o` gives no warnings about test files in `app/`;
  - `php artisan test` passes;
  - a temporary colocated test under `app/` is discovered, then removed.

## Calls made without Rob's explicit input

- Review skills run at the end of each `/feature` task and can also be run on their own.
- Rules go in `.claude/rules/`, not `CLAUDE.md` (which Boost regenerates) or Boost's `.ai/` directory.
- Each module has its own service provider, listed in `bootstrap/providers.php` with no custom loader. Modules only talk to each other through their Application layer.
- The destructive-command guard also covers non-force recursive `rm`, stash drop/clear, `git branch -D`, discarding file changes, and the database wipe/fresh/reset commands.
- Dependency changes prompt through a hook that asks with a reason. Edits to the guard files prompt through `ask` rules, so that protection doesn't depend on the hooks it protects. Both override Rob's allow list.
- This design doc is committed in the PR, as evidence of how AI was used. Rob's Lerd files stay out of these commits.
- `tests/` keeps only the architecture tests and the Pest bootstrap.
- Superpowers is declared as a project plugin rather than documented as a per-developer install. Rob didn't answer this one, so it is the recommended option.
- Three commits as listed.
- Minimum release age of 7 days.
- The dependency tree is a table plus a Mermaid graph.
- Hooks are bash + jq, each with a colocated bash test.
- The destructive-command guard is deliberately conservative about quoted text.
- ESLint + Prettier + Vitest are proposed for the frontend commit, which is out of scope here.
